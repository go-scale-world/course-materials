Retrieval-Augmented Generation (RAG)

Look up the facts first, then answer the question. Read through the notes, expand what you need, and test yourself along the way — the source notes stay exactly as written.

Let's start with an example

My payment failed.

Say you message Netflix support: "My payment failed."

Without RAG

the support bot just answers from what it already "remembers" from training. So you get something generic, like "please try again later" — it doesn't actually know what worked for anyone else in this exact situation.

With RAG

the system quickly searches through thousands of old support tickets, finds the ones closest to your problem, checks what actually solved them, and then answers you using that real info.

Same question, two very different answers. The difference is simple — in the second case, the system looked something up first, instead of just guessing from memory. That's basically the whole idea of RAG.

So, what is RAG?

Simple definition

🧠 RAG means

Look up the facts first, then answer the question.

That's really it at the core. Instead of the AI just answering from memory, it goes and checks real documents first, and then uses what it found to write the answer.

Does this question even need RAG?

General knowledge, or something only your documents know?

Not every question needs a lookup — RAG is only really useful when the answer depends on something the model doesn't (and can't) already know. A decent way to check: is this general knowledge, or is it something specific, private, recent, or already given to me?

Worth keeping in mind

RAG doesn't make the model "smarter" or better at reasoning or math. It just gives it access to information it didn't have. If a question can already be answered with general knowledge, plain logic, or something already pasted into the chat, adding RAG just adds cost and delay for no real benefit.

The problem

Why do we even need this?

Think of a normal LLM as a student sitting a closed-book exam. Whatever they memorized while studying is all they've got in the room with them. This creates a few real problems:

Old information+
The model was trained once, on data up to some date. Anything that happened after that date just doesn't exist for it.
Making things up+
When it doesn't know something, it usually won't say "I'm not sure." It tends to guess anyway, in a way that sounds confident — even when it's wrong. This is what's called hallucination.
No access to private stuff+
The model was never shown your company's internal documents, last week's meeting notes, or one specific customer's ticket history. It genuinely has no way to know things it was never trained on.

You can see this problem in a lot of places — a legal assistant that has no idea about a law passed last month, a support bot that can't see your company's real tickets, a doctor's assistant that can't check the newest research. In each case, the model is stuck with only what it happened to memorize a while ago.

🧠 Remember this

A normal LLM sits a closed-book exam — memory only, nothing to check. RAG turns it into an open-book exam — it can flip to the right page before it answers.

How RAG works

The journey

RAG happens in two stages, and they don't happen at the same time — this is the part people usually mix up:

  1. Ingestion — happens first, one time (or updated every now and then), before anyone even asks a question. It's about preparing the documents so they're ready to be searched.
  2. Retrieval — happens every single time someone asks a question. This is the actual "finding the answer" step.
🧠 Remember this

Ingestion builds the book. Retrieval reads from the book. You can't read a page that was never organized into the book to begin with.

Say a company has 1,000 employee policy documents. The AI can't just "search a folder" the way you search files on your laptop — the content needs to be turned into something it can compare by meaning. Here's roughly how that happens:

  1. Chunks — the big documents get split into small pieces, called chunks. Feeding an entire 200-page manual to the model in one go would be messy, so smaller pieces work better.
  2. Embedding — each chunk goes through an Embedding API, which converts the text into a list of numbers. This is what lets the system realize "remote work" and "work from home" are basically saying the same thing, even with different words.
  3. Semantic Index — all these number-versions get organized into a semantic index, which is basically a smart index built to search by meaning, not exact wording.
  4. Everything gets stored together as the Knowledge Base — the final, ready-to-search set of chunks plus their number-versions.

Now that the "book" is ready, retrieval kicks in live, every time someone asks something:

1
Question
→
2
Query Embedding
→
3
Semantic Search
→
4
Top-K Chunks
→
5
Augmentation
→
6
LLM → Answer
  1. The user's question also gets converted into numbers — this is the query embedding — using the same method as before, so it can actually be compared fairly.
  2. A similarity search compares the question's numbers against every chunk's numbers in the Knowledge Base, to see which stored chunks are closest in meaning. This is also called semantic search.
  3. The closest matches get picked — you choose how many with Top K (K = 3 means "give me the top 3 matches"). These are the ranked results.
  4. Those chunks get augmented onto the original question — basically attached as extra context — and the whole thing is sent to the LLM.
  5. The LLM generates the final answer, using the question and the real facts it was just handed.
🧠 Remember this

Retrieval works a bit like a librarian, not a genius with perfect memory. The AI already "knows books exist" thanks to training, it just doesn't know which shelf holds the answer. RAG is what tells it exactly where to look.

Big picture

Putting it all together

RAG exists because AI models are stuck in time, sometimes make things up, and can't see your private information. Instead of retraining the whole model every time something changes — which is slow and expensive — RAG keeps the model as it is, and just gives it a way to search your own documents right when it needs to answer. Ingestion prepares that search once. Retrieval uses it every single time a question comes in. The retrieved facts get attached to the question so the model answers from real evidence instead of a guess — basically turning a closed-book exam into an open-book one.

Quick memory

Six things to keep

  • ✓RAG, simply: look up the facts first, then answer.
  • ✓Full version: Retrieve facts + Augment the question with them + Generate the answer.
  • ✓Fixes three LLM problems: old information, hallucination (made-up facts), and no access to private data.
  • ✓Two stages: Ingestion (prepare documents, once) → Retrieval (search + answer, every time).
  • ✓Quick check: "Is this general knowledge, or something only my own documents would know?" — that tells you whether RAG is worth it.
  • ✓Trade-off: better accuracy and fresher answers, but a bit slower and a bit costlier.
RAG's full picture

Retrieval + Augmentation + Generation

Once we go a little deeper, RAG is really made up of three steps, and the name spells them out:

R
Retrieval

Go find the relevant facts.

→
A
Augmentation

Add those facts onto the user's question.

→
G
Generation

The model writes the answer using the question plus those facts.

Back to Netflix: retrieval is searching old tickets, augmentation is attaching the best-matching past solutions to your question, generation is the bot writing an answer using both your question and those real solutions.
