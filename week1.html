1. The AI We Already Know

Let's start with something familiar. Most of us have used tools like ChatGPT. You type a question, and it answers. You ask it to write something, and it writes it. You ask it to explain something, and it explains it.

This is the AI most people already know:

  • It can write things — emails, messages, stories, code.
  • It can summarize things — turn a long article into a short one.
  • It can answer questions — almost like a very well-read friend.
  • It can generate code — if you describe what you want, it can write it for you.

This is genuinely useful. But here's the thing to notice: in every single one of these examples, you are the one driving. You ask, it answers. You ask again, it answers again. It never moves on its own.

Keep that observation in your pocket. It matters a lot in a minute.

2. What It Can't Do

Now let's flip the coin and look at the limits of this same AI — the ones we don't usually notice because we're used to working around them.

  • It can't act on its own. It can tell you how to send an email, but it won't actually send it. You still have to do that part.
  • It forgets things. Unless you remind it, it doesn't remember what happened two messages ago. Every reply depends on what you just said, not what came before.
  • It doesn't check its own work. If it makes a mistake, it won't notice unless you point it out.
  • It always waits. It never decides to do something by itself. It sits there until you type the next instruction.

Think about what this means in a real work setting. Imagine a company gets 200 support tickets a day. A regular AI tool can help write a reply to one ticket. But it can't:

  • Notice that 15 of those 200 tickets are actually about the same problem.
  • Decide on its own which ones are urgent.
  • Prepare a report and send it to the right person.

A human still has to do all of that noticing and deciding. The AI is a helpful pen, not a helpful employee. This gap — between just answering and actually handling things — is exactly the gap we need to close.

3. Enter Agentic AI — The Saver

This is where Agentic AI walks in.

If the last section was about an AI that only answers when asked, Agentic AI is about an AI that can decide what needs to be done, and go do it — with a goal in mind, not just a question to answer.

It's not a new kind of magic. It's the same kind of AI model we just talked about, but now it's allowed to:

  • Look at information on its own.
  • Make small decisions along the way.
  • Take steps, one after another, toward a goal.
  • Use tools to actually get things done, not just describe them.

It's the "saver" because it picks up exactly where the regular AI stopped — right at the point where a human had to step in.

4. Basic Definition

Now that we've felt the gap and seen what fills it, here's the plain definition:

Agentic AI is an AI system that can decide, act, and work toward a goal — with less step-by-step instruction from a human.

Instead of just replying to one message, it can look at a situation, figure out what needs to happen, do it in steps, and only come back to a human when it truly needs help or approval.

5. Gen AI vs Agentic AI

Now that we've lived through both sides, here's the same idea laid out clearly:

Gen AI (like ChatGPT)Agentic AI
How it worksAnswers one prompt at a timeWorks through a goal in multiple steps
MemoryUsually forgets past steps unless remindedCan remember and use past information
ActionOnly describes what to doCan actually take the action
Decision-makingMakes no real decisions, just respondsMakes small decisions along the way
Human involvementNeeded at every single stepNeeded mainly for approval or unclear cases

Nothing here is "one is bad, one is good." Agentic AI is simply Gen AI with more responsibility handed to it.

6. Applications in Enterprises — A Quick Overview

Companies are already using this idea in real, practical ways:

  • Support ticket triage — reading tickets and sorting them by product, urgency, and topic.
  • IT monitoring — watching system logs and deciding when something needs a human's attention.
  • Sales lead qualification — checking incoming leads and passing only the good ones to a salesperson.
  • Invoice checking — matching an invoice against a purchase order and flagging mismatches.

The common thread in all of these: a repetitive judgment call that used to need a human's constant attention, now handled by something that watches continuously and only escalates when needed.

7. One Example, Broken Down Properly

Concepts stick better with a real example. So let's do this in three parts: first a simple everyday example that uses the real building-block concepts of agentic AI, then a one-page glossary of those exact concepts, and finally our actual course project explained the same way.

7.1 A Simple Example, Using the Real Building Blocks

Imagine a Trip Planning Agent — you tell it "plan me a 3-day trip to Goa," and it takes it from there.

Here's what actually happens behind the scenes, step by step:

  1. The LLM (the brain) — a large language model reads your request and understands what you actually want: 3 days, Goa, and it needs to figure out flights, stay, and a day-by-day plan.
  2. Tooling (the hands) — the agent doesn't know flight prices or hotel availability by itself, so it uses tools — a flight-search tool, a hotel-search tool, a weather tool — the same way you'd open different apps to check different things.
  3. RAG — Retrieval-Augmented Generation (the memory lookup) — before suggesting anything, it retrieves your past trip notes (maybe you once wrote "I don't like early morning flights"), and uses that real information instead of guessing.
  4. Multi-Agent Architecture (the team) — instead of one single agent doing everything, the work is split — one smaller agent handles flights, another handles hotels, another puts the final itinerary together. They coordinate like a small team, not one overloaded worker.
  5. MCP — Model Context Protocol (the universal plug) — each tool (flights, hotels, weather) connects to the agent through one standard connection method, instead of needing custom wiring for every single tool.
  6. Feedback (the correction loop) — if you say "no, I don't want that hotel," the agent doesn't just apologize — it adjusts its next suggestion based on that correction.

Notice this wasn't one big magic step. It was the LLM thinking, tools acting, RAG grounding it in real facts, multiple agents splitting the work, MCP connecting everything cleanly, and feedback correcting it along the way. This exact pattern is what we'll now name properly, and then reuse for our own project.

7.3 Now the Same Concepts, Applied to EPC

Our course project is called EPC — Enterprise Problem Consolidation Agent. It deals with customer support tickets. Let's explain it using the exact same six concepts:

  • LLM — Gemini reads each incoming ticket and understands what it's actually about — the product, the issue, how it's phrased.
  • Tooling — the agent uses tools to look things up and take action — checking ticket history, searching for related cases, and later, sending notifications.
  • RAG — before deciding how serious a ticket is, EPC retrieves related historical incidents from Google Drive and a vector search system, so its judgment is grounded in real past cases, not guesses.
  • Multi-Agent Architecture — the work is split across four coordinated agents: one extracts meaning from the ticket, one clusters similar tickets together, one scores business impact, and one prepares the escalation for a human.
  • MCP — this is how EPC connects cleanly to enterprise tools like Gmail, Drive, and Chat, without needing custom code for every single one.
  • Feedback — when a human approves or rejects an escalation, that decision feeds back into the system, shaping how it behaves next time.

Same six building blocks. Same pattern from the trip planner. Just applied to a real business problem — catching an emerging issue within minutes, instead of after a hundred people have already complained.

8. The First Step in Working With AI — The Prompt

So — how do we actually talk to something like this? Every single interaction, no matter how smart the agent is, starts the same way: with a prompt.

A prompt is simply the instruction we give the AI — in plain words, telling it what we want it to do.

This is the real starting point of working with any AI, agentic or not. Get the prompt wrong, and everything downstream — decisions, actions, results — goes wrong too. So this deserves real attention.

To keep things simple and easy to follow, we'll use one running example through this whole section: an AI that generates study notes from a topic — the same kind of task we're doing right now, in this very document.

9. Prompt Building — How to Actually Write One

A weak prompt is vague. A strong prompt is specific. Let's see both, using our notes-generation example.

Weak prompt

"Make notes on this topic."

This doesn't say what "notes" should look like. How long? What sections? With examples or without? The AI has to guess — and guesses are inconsistent.

Strong prompt

"You are a note-making assistant. Read the topic below and create notes with: a short definition, 3–5 key points, and one simple example. Topic: [topic text]"

Notice what changed:

  • It tells the AI what role to play ("You are a note-making assistant").
  • It tells the AI exactly what the notes should contain — no guessing.
  • It gives the exact topic to work on.

A good prompt removes guesswork. That's the whole goal.

10. Types of Prompting

There are a few well-known ways to write prompts that consistently get better results.

Instead of just describing what you want, you show an example of the input and the correct output, right inside the prompt.

Example:

Topic: "Photosynthesis"
Notes: Definition — how plants turn sunlight into food. Key points — happens in leaves, needs sunlight/water/CO2, produces oxygen. Example — a plant near a window grows better than one in a dark room.

Now do the same for this topic: [new topic]

Showing even one solid example makes the AI's notes far more consistent, because it's copying a pattern instead of guessing a format.

This means asking the AI to think through the problem step by step, out loud, before giving a final answer — instead of jumping straight to a conclusion.

Example: "First, list the main ideas in this topic. Then, decide which ones are essential and which are extra detail. Only after that, write the final notes."

This works especially well for anything that needs judgment, not just simple lookup — like deciding which points in a topic actually deserve a place in the notes.

11. Prompt Categories

Along with types of prompting, there are also categories of prompts — based on who the instruction is really coming from.

  • System Prompt — the background rules and role you set for the AI before the conversation even starts. Think of it as the AI's job description. Example: "You are a note-making assistant. Always write notes in simple language with a definition, key points, and one example."
  • User Prompt — the actual request being made in the moment. Example: "Here's today's topic — generate notes for it."

People often mix these up. The system prompt sets the behavior. The user prompt is the actual task for right now. Keeping them separate makes the AI's behavior far more predictable — especially when the same system prompt is reused for hundreds of different topics.

LLM Fundamentals

An LLM, or Large Language Model, is a program trained on huge amounts of text. It does not think like a person. It predicts the next word, one at a time, based on patterns it learned.

Learning phase

Training

The process of showing the model huge amounts of text, so it learns language, facts, and patterns.

Examples: Books, websites, and code.

Word pieces

Tokens

Small pieces of text, like parts of a word. The model reads and writes text one token at a time.

Example: "un" plus "happy" makes unhappy.

Internal settings

Parameters

The internal settings the model learns during training. More parameters usually means it can understand more complex patterns.

Examples: Billions to trillions of parameters.

Memory size

Context Window

How much text the model can see and remember at once, in a single conversation.

Examples: From a few thousand to millions of tokens.

SLM: Small Language Models

An SLM is a smaller version of an LLM. It has fewer parameters, so it needs less computing power, but it is still trained to understand and write language.

FeatureLLMsSLMs
SizeVery large, billions of parametersSmaller, millions to a few billion parameters
SpeedSlower, needs more computing powerFaster, needs less computing power
Where it runsMostly in the cloud, on big serversCan run on a phone or laptop
Best forComplex reasoning, broad knowledgeSimple, fast, focused tasks

The practical takeaway

LLMs are a strong choice when an agent needs broad knowledge and complex reasoning. SLMs are useful when speed, lower cost, or running locally matters more.

12. Metrics — The Settings That Shape the Output

Beyond what we ask for, we can also control how the AI generates its answer, using a few key settings. These matter a lot for something like notes generation, where you might want factual, focused notes one time and more creative, exploratory notes another time.

  • Temperature — controls how "safe" or how "creative" the AI's wording is. A low temperature (like 0.2) gives focused, predictable notes — good for factual topics. A high temperature (like 0.8) gives more varied, creative wording — good for brainstorming, but riskier for accuracy.
  • Top-p (nucleus sampling) — controls how many different word choices the AI is allowed to consider at each step. A lower value keeps it narrow and safe; a higher value lets it explore more options.
  • Max tokens — sets a limit on how long the output can be. Useful so your "notes" don't accidentally turn into a five-page essay.
  • Frequency penalty — discourages the AI from repeating the same words or phrases too often, which keeps notes from feeling repetitive.

For notes generation, a common practical choice is a low-to-medium temperature — enough to sound natural, but focused enough to stay accurate and consistent.

13. When the Output Isn't What We Intended — Schema Validation

Even with a great prompt and well-tuned settings, the AI won't always return exactly what we asked for. Sometimes the "key points" section is missing. Sometimes it forgets to include an example. Sometimes it returns one giant paragraph instead of clean, separated sections.

This is where schema validation comes in.

A schema is simply a strict definition of what the output should look like — which fields are required, and what type each one should be. For our notes example, that might mean: a title (text), a definition (text), key points (a list, not a paragraph), and an example (text) — all required, every time.

Schema validation means checking the AI's output against that form before we trust it. If something is missing or in the wrong shape, we reject it and either ask the AI to try again or flag it for a human — we never let broken data quietly move forward.

This is exactly why schema validation helps:

  • It catches bad or missing data early, before it causes problems further down the line — like notes with no example, or no key points.
  • It forces consistency, so every set of notes follows the same reliable structure.
  • It builds trust in the system, since we're not just hoping the AI got it right — we're checking.

This connects straight back to prompting — the better your prompt (especially with a good few-shot example) and the better-tuned your settings, the more often the output passes validation on the very first try.

14. Coded AI Agents vs Non-Coded (No-Code) Agents

There are two broad ways to build agents like this:

  • No-Code Agents — built using drag-and-drop tools and visual builders. Quick to set up, no programming needed, good for simple, well-defined tasks.
  • Coded Agents — built by actually writing code (like what we're doing in this course). Takes more effort upfront, but gives full control over logic, memory, tool use, and how the agent behaves in tricky situations.

Both have a place. No-code tools are great for quick, simple automations. But once a system needs to handle messy real-world situations — multiple tools, custom logic, precise control over decisions, integration with a company's actual systems — a no-code tool starts to hit a wall.

This is exactly why learning to build coded agents is the skill worth investing in. It's the version that doesn't box you in. You're not limited to what a drag-and-drop tool allows — you can build exactly what the situation needs, connect it to any system, and fix it precisely when something goes wrong. Every advanced capability in this course — memory, multi-agent coordination, tool use, safety checks — is only fully possible when you're working at the code level.
