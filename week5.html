Part A

Why Does an LLM Need More Information?

An LLM (Large Language Model) is a computer program trained to understand and generate human language.

Fixed Knowledge

Generic answers, like what photosynthesis is. Works well on its own.

Changing Info

Not fixed, like today's weather, which is different every few hours. Needs outside help.

Key idea

An LLM's knowledge is fixed at the point it was trained. Fast-changing information needs a way in from outside.

Where Does This Information Come From?

An LLM cannot always rely only on what it already knows. It needs a way to bring in information from outside itself: documents, databases, websites, or other services.

Example: "What is the weather in Kanpur right now?" The AI cannot guess this on its own. It asks a weather service, which holds live, constantly updated data. The service processes the request and sends the current data back. The AI uses this data to answer, working with an outside system, not alone. This communication between two software systems happens through an API.

Part B

What Is an API?

Definition

API stands for Application Programming Interface, a defined way for one software system to send a request to another and get a response back.

Analogy: a waiter in a restaurant

The customer never walks into the kitchen. The order goes to the waiter, who carries it to the kitchen and brings the food back. The customer never needs to know how the kitchen works.

Every Service Works Differently

Not every API is built the same way. Each company sets its own rules for requests and responses.

Imagine every restaurant taking orders differently: one only accepts written notes, another needs a phone call, another needs an app. A person ordering from many restaurants must learn a new method each time. Developers face the same problem: one new method per service.

Part C

The Real Problem

APIs themselves are not badly designed. They are genuinely useful.

The real difficulty

Every service follows its own separate approach. Developers must build and maintain a different connection for every service, and it gets harder as more are added. This is the exact gap that MCP was created to solve.

Part D

Enter MCP: What Is It and Why Do We Need It?

Definition

MCP stands for Model Context Protocol, a common, standard way for AI applications to connect with external tools and information.

One AI application. One clean connection to MCP. MCP branches out neatly to every service.

  • MCP does not replace APIs. An MCP Server can still use APIs behind the scenes.
  • MCP changes the front-facing side: how the AI connects to these capabilities.
  • Instead of a different method per service, there is one shared approach.

API vs MCP

AspectAPIMCP

MCP is not a competitor to APIs. It works alongside them, not instead of them.

Part E

The MCP Architecture

MCP has three main parts that work together, each with a distinct role: the Host, the Client, and the Server.

Analogy: a food delivery app

The app is the Host, a delivery agent is the Client, and the restaurant kitchen is the Server.

Definition: the Host is the main AI application the user directly interacts with, and which manages the overall use of MCP.

One Host can connect to more than one MCP Server at a time. It uses an MCP Client to manage each connection.

Example: a single app connecting out to a Weather Server, a GitHub Server, a Slack Server, and a Database Server, all at once. One app, many connections.

Definition: the MCP Client connects the Host to a specific MCP Server and manages communication between them.

The Client sends requests to the MCP Server on behalf of the Host, and receives back the results. An AI application may use a separate Client for each server it connects to.

One Client per Server: a clean, dedicated connection each time.

Definition: the MCP Server provides capabilities, such as tools or information, to the AI application, through the Client.

One server hub can connect to several systems at once, such as GitHub, Slack, a database, and files.

Part F

What Can an MCP Server Provide?

An MCP Server can offer more than one type of capability. The three main types are Tools, Resources, and Prompts.

🍲 Tools

A Tool is a capability that lets the AI perform an action. Asking the kitchen to actually cook a dish, a real action.

Examples: checking the current weather, searching a GitHub repository, creating a new GitHub issue, sending a message through Slack.

📖 Resources

A Resource gives the AI access to information it can use while forming an answer. Checking what ingredients are in the pantry, without cooking anything yet.

Example: a company's leave policy document. The AI reads from this resource for an accurate answer. No action is performed, only information is supplied.

📋 Prompts

A Prompt, in the MCP context, is a ready-made, reusable instruction or template that guides the AI on how to carry out a task. A written recipe card kept in the kitchen for a dish that is often made, so it comes out the same way every time.

Examples: a code review prompt that reviews code consistently, or a document analysis prompt with fixed steps to follow.

In short: Tools are things the AI can do. Resources are things the AI can read. Prompts are ways to guide the AI. Together, these let an AI application do more than generate text: it can act, read, and follow consistent instructions.

Discovery: how does the AI know what is available?

Discovery is the process through which an AI application learns what capabilities an MCP Server provides. The server describes itself to the AI, so capabilities do not need to be hard-coded ahead of time. As new tools are added, the AI learns automatically.

Why MCP Matters

Before

A separate method for every service: Weather, GitHub, Slack, and the database each need their own connection built and maintained.

After

One shared standard for every service, through MCP. The AI app connects once, and MCP branches out to Weather, GitHub, Slack, and the database.

AI applications increasingly need to take actions, access live information, and connect with many services. MCP gives AI applications one common way to connect with tools, resources, and prompts. It works alongside existing APIs, and capabilities can be discovered automatically.

Big idea

MCP helps AI applications connect to the outside world in a more consistent way.

In-class activity: Password, Agentic AI edition

A quick group game to practice giving precise, single-word prompts. Students split into two teams; each round one Clue Giver from a team sees a secret word and can give only one word as a clue. The team gets one guess. If wrong, the Clue Giver gives one more single word, never repeating a clue and never saying the answer itself. Each word has a 30 to 45 second time limit. The first team to guess correctly scores a point, the Clue Giver role rotates every round, and only spoken words count, no hand signs, sounds, or spelling out letters. Most points when time is up wins.

Part H

Types of RAG Architectures

Eight retrieval strategies, roughly in order of sophistication. This week's lab build uses architecture 4, Re-Ranking RAG.

1. Naive RAG Semantic search only+

Retrieves relevant text purely by comparing meaning: the query and documents are embedded as vectors, and the closest matches are pulled in as context.

Query
→
Embed Query & Docs
→
Vector Search (top-k)
→
Answer

Example: a FAQ chatbot that finds the most relevant help center article for a customer's question, even if they do not use the exact wording.

2. Keyword RAG Lexical / BM25 search+

Retrieves documents by matching the exact words and phrases in the query, using classic scoring methods like BM25 or TF-IDF, with no embeddings involved.

Query
→
BM25 / TF-IDF Scoring
→
Matched Documents
→
Answer

Example: searching legal contracts for an exact clause number, or a support system searching for a specific error code like ERR_504.

3. Hybrid RAG Semantic + keyword, combined+

Combines semantic and keyword search so results are relevant both in meaning and in exact wording, then merges the two rankings into one result set.

Query
→
Semantic + Keyword Search
→
Merge & Score
→
Answer

Example: the EPC platform matching a ticket's general topic (semantic) and its literal error code or product name (keyword) at the same time.

4. Re-Ranking RAG This week's build+

Takes the candidates from a hybrid search and asks a second, stronger model to re-score them, keeping only the results that are genuinely most relevant.

Query
→
Hybrid Retrieve (wide set)
→
Gemini Reranker
→
Top Results
→
Answer

Example: this week, Gemini re-ranks historical incidents so the escalation report cites the single most relevant past case, not just the closest keyword match.

5. Agentic RAG An agent decides when to retrieve+

Lets an LLM agent decide, on its own, whether retrieval is even needed and how many times to search, rather than always retrieving once by default.

Example: a research assistant that decides on its own whether it needs internal documents, a web search, or both before it answers.

6. Graph RAG Retrieval over a knowledge graph+

Stores knowledge as entities and relationships in a graph, then retrieves by traversing those connections, capturing context that plain text search would miss.

Example: a support system that traces how one incident connects to related tickets, root causes, and past fixes.

7. Corrective RAG Self-checks retrieval quality+

Grades retrieved documents for relevance before using them, and automatically falls back to another source, such as a web search, when the match is weak.

Example: a fact-checking tool that falls back to a live web search when its internal document store returns weak matches.

8. Multimodal RAG Retrieves text, images and tables+

Retrieves across different content types at once, such as text, images, and tables, so an answer can draw on whichever format actually holds the information.

Example: a product-support agent that retrieves both a manual's written steps and the matching diagram.

Lab 5, Agentic AI EPC Pipeline

Real Tools & Real Retrieval

MCP integrations for Drive, Gmail and Discord, plus hybrid RAG with re-ranking.

This week connects the platform to three external tools: Google Drive, Gmail, and Discord. The Escalation Preparation Agent reads a runbook stored in Drive, creates a draft email in Gmail, and posts an alert to a Discord channel. These tools are exposed through MCP, a standard protocol that lets any compatible AI client call them the same way. Retrieval is also upgraded this week: instead of relying on semantic search alone, the system combines semantic search with keyword search, then uses Gemini to re-rank the results before they are used in a report.

Three New Integrations

Drive and Gmail via OAuth, Discord via a webhook.

One Standard Protocol

MCP tools, usable by any compatible AI client.

Runs Locally This Week

OAuth needs personal authorization, so these tools run on a local machine, not Cloud Run.

This Week's Goal

Connect the platform to real enterprise tools, and sharpen retrieval accuracy with a re-ranking step.

  1. Google Drive integration: pull a relevant runbook excerpt into escalation reports.
  2. Gmail integration: auto-draft, never auto-send, a stakeholder notification email.
  3. Discord integration: post a real-time alert to a Discord channel via webhook.
  4. A real MCP server: expose these tools via the actual Model Context Protocol, usable by any MCP-compatible client.
  5. Hybrid RAG with re-ranking: combine semantic and keyword search, then have Gemini re-rank the results.
