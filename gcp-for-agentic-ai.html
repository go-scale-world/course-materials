Getting Started with Google Cloud Platform for Agentic AI

Part 1

The Problem: Personal Scale vs Enterprise Scale

Most agentic AI projects begin as a small idea. The difficulty starts when that idea has to serve more people, handle more data, and run without anyone watching it.

A Personal Problem

Take a person who spends too much time on email, travel plans, and monthly bills. To save time, this person builds a small AI agent on a laptop that reads mail, drafts replies, and tracks due dates.

It runs on one machine, uses one API key, and handles a handful of requests a day. Nothing is shared with anyone else, so there is very little to protect or manage. Small problems still show up: the agent stops when the laptop closes, the API key sits directly in the code, and conversation history disappears on restart. One person can live with that.

An Enterprise Problem

Now take a company with 10,000 customers who write in every day. The agent has to be available around the clock, serve thousands of people at once, and stay quick during a festival sale. A laptop cannot do this.

The agent handles customer data and takes real actions, so the company needs to control who can access what, keep a record of every action, protect passwords and keys, follow data protection rules, and keep model costs under control. Once there are more than a few agents, nobody can say with confidence which ones exist, what tools they use, or what they are allowed to touch.

Personal vs Enterprise at a Glance

AreaPersonal ProblemEnterprise Problem
UsersOne personThousands of customers and employees
AvailabilityWorks while the laptop is onMust run 24/7
DataA few emails and filesLarge, sensitive data spread across many systems
AccessOne key, one userMany roles, teams, and agents with different permissions

MemoryLost when the program restartsStored safely and carried across sessions
OversightThe person notices when it breaksNeeds a record of every agent, tool, and action
CostA few small callsMust be tracked, limited, and optimized
Key idea

The agent itself does not change much between the two cases. What changes is everything around it, and that surrounding work is where most of the effort goes at enterprise level.

How GCP Helps

A personal builder needs an idea and a laptop. An enterprise needs a full platform behind the idea, and GCP is built to be that platform.

Part 2

Why Use GCP?

An agentic AI application is more than one call to a language model. It needs a model to reason, tools to act, memory to store information, and security rules to keep everything in check. Building all of that separately takes a long time and leaves many places for things to go wrong.

One place for everything

Models, hosting, databases, security, and monitoring all sit on a single platform, so the team spends less time connecting vendors and fixing the gaps between them.

A strong AI foundation

GCP provides the Gemini models, plus a catalogue of models from other providers. A team can pick the model that suits the task and change it later without rebuilding the application.

Built for agents

Since April 2026, Google's AI platform has been organized around agents, so building, running, securing, and improving them are all handled in one place.

Every agent is governed

Each agent can receive its own identity, be listed in a central registry, and have its tool calls checked by a gateway.

Scales with demand

The same application can serve a few test users or thousands of real ones. Capacity grows and shrinks automatically, and billing follows actual usage.

Works with existing data

Many organizations keep data in BigQuery or Cloud Storage, and agents on GCP can read from there directly without copying it elsewhere.

Put simply, GCP gives a team the model, the hosting, the memory, and the safety rules for an agent in one place.

Part 3

Introduction to GCP

Definition

Google Cloud Platform (GCP) is a set of cloud services offered by Google. Instead of buying and maintaining its own servers, an organization rents computing power, storage, databases, and AI tools from Google over the internet.

  • Billing is based on usage, such as compute time, storage size, or the number of model calls. There is no large upfront hardware cost.
  • Google runs data centers in many regions around the world. A team picks a region close to its users, or one that satisfies its data location rules.
  • For many services, Google manages the servers, updates, and scaling. The developer only supplies code or configuration.
  • There are three common ways to work with GCP: the Cloud Console (web interface), the gcloud CLI (command line), and APIs with client libraries (from code).

A quick note on naming

In April 2026, at Google Cloud Next, Vertex AI was renamed the Gemini Enterprise Agent Platform. Existing Vertex AI workloads carry forward under the new name. A similar thing happened to Agent Engine, now called Agent Runtime. Do not mix this up with Gemini Enterprise, which sounds almost the same: Gemini Enterprise is the app employees use, licensed per user, while the Agent Platform is what developers use to build agents, billed by consumption. This guide uses the new names and mentions the old ones where it helps.

Part 4

Parts of GCP That Matter for Agentic AI

The services below are grouped by the job they do in an agentic application.

4.1 The Agent Platform: the Brain and the Control Room

The Gemini Enterprise Agent Platform is organized around four ideas.

  • Gemini models are the reasoning engine. The Gemini 3 family is current, with the older Gemini 2.5 models being retired.
  • Model Garden is a catalogue of models, listing Gemini alongside models from other providers, so a team can compare and choose.
  • Gemini API and Google AI Studio offer a light way to begin, testing prompts and building a prototype before moving to the full platform.
  • Agent Development Kit (ADK) is an open source framework for writing agents in code. It is model-agnostic and available in Python, Go, Java, and TypeScript.
  • Agent Studio is a low-code visual tool for building and trying out agents quickly.
  • Agent Garden holds ready-made agent templates for common jobs such as customer service and data analysis.
  • Agents CLI is a command line tool for working with the platform.
  • Open protocols such as MCP (connecting agents to tools) and A2A (agents talking to other agents) let agents work with tools and agents built elsewhere.
  • Agent Runtime is the managed place where agents are hosted and served. It supports long-running agents that keep their state, along with sessions, and it handles the scaling.
  • Memory Bank gives an agent long-term memory, picking out and storing useful facts about a user across conversations, so the agent can carry on later without starting from zero.
  • Agent Identity gives every agent its own unique identity, so permissions and audit records can be tied to that specific agent.
  • Agent Registry is a central catalogue of approved agents and tools. Agents deployed on the platform are registered there automatically.
  • Agent Gateway is a control point that checks authentication, applies policies, and governs the tool calls agents make. It works together with Model Armor, which screens prompts and responses for risky content.
  • Agent Simulation tests an agent against made-up user conversations before real users ever see it.
  • Agent Evaluation scores how well the agent behaves, including on live traffic.
  • Agent Observability shows the agent's steps and tool calls, making it far easier to understand why it answered the way it did.
  • Agent Optimizer helps improve an agent's prompts by looking at where it failed.

4.2 to 4.6: The Rest of the Platform

4.2 Compute Where the code runs+

Agent Runtime is the first choice for hosting agents on the platform.

Cloud Run runs containerized code and scales automatically, even down to zero when nobody is using it. It is a common choice for custom backends and tool APIs.

Cloud Run functions run small pieces of code in response to events, suiting simple tools like looking up an order status.

Google Kubernetes Engine (GKE) is meant for large or complex systems that need close control over containers, and asks for more setup and operational skill.

Compute Engine provides virtual machines, used when full control over the machine is needed, for example for special software or GPUs.

4.3 Data & Memory What the agent knows and remembers+

Cloud Storage holds files such as PDFs, images, and documents the agent may read.

BigQuery is a data warehouse for large scale analysis. Agents can use it to answer questions over business data.

Firestore is a flexible document database, working well for app data such as user preferences and chat records.

Cloud SQL and AlloyDB are managed relational databases holding structured business data. AlloyDB can also support vector search.

RAG Engine and Vector Search help an agent find relevant information in large sets of documents, the base for Retrieval-Augmented Generation.

Memory Bank handles what the agent should remember about each user over time.

4.4 Integration & Orchestration Connecting the pieces+

Pub/Sub passes messages between services, letting parts of the system work independently and cope with sudden bursts of requests.

Cloud Tasks queues work for later and retries it when it fails.

Workflows runs a fixed sequence of steps across services, suiting processes where the order must always stay the same.

Eventarc triggers actions when something happens, such as a new file arriving in storage.

Apigee and API Gateway manage and protect the APIs that agents use as tools.

4.5 Security & Access The safety rules+

IAM controls who can do what on which resource, covered in detail in Part 6.

Agent Identity brings agents into IAM as identities of their own, next to people and service accounts.

Service accounts are identities for applications, as opposed to people.

Secret Manager stores API keys and passwords safely so they never appear in code.

VPC Service Controls and private networking keep sensitive data inside a defined boundary.

Agent Gateway and Model Armor check what goes into and comes out of the agent.

4.6 Monitoring & Cost Keeping control+

Cloud Logging, Monitoring, and Trace record what the application did, how fast it ran, and where it failed.

Agent Observability adds a view specific to agents, such as their reasoning path and tool calls.

Billing budgets and alerts warn the team when spending crosses a set limit. This matters because model calls can add up quickly.

A Practical Way to Choose

  1. Start small. Use AI Studio to check that the idea works.
  2. Move to the Agent Platform once the application needs security, scale, and governance.
  3. Pick the simplest hosting option that fits. Agent Runtime or Cloud Run covers most cases, and GKE makes sense only when a clear need appears.
  4. Turn on the governance pieces (identity, registry, gateway) before the number of agents grows, not after.
  5. Add data services only when the agent actually needs them.
Part 6

Providing Access: IAM Basics

Agents can read data and take actions, so access has to be planned with care. GCP handles this through IAM.

The Three Parts of an Access Rule

PartMeaningExample
Who (principal)The person, group, agent, or service account receiving accessA developer, a team group, or an agent's identity
What (role)A bundle of permissionsAgent Platform User, Storage Object Viewer
Where (resource)The level at which the role appliesA project, a bucket, or a dataset

Types of Roles

Basic Roles

Owner, Editor, Viewer. Very broad, fine for learning, but should be avoided in production.

Predefined Roles

Created by Google for specific services. These are the usual choice.

Custom Roles

Let the team build an exact set of permissions when no predefined role fits.

Key Principles

  • ✓Least privilege. Every person and agent should get only the access needed for the job. An agent that only reads documents should not be able to delete them.
  • ✓Groups over individuals. Giving a role to a group is easier to manage than assigning it to many separate users.
  • ✓One identity per agent. With Agent Identity, each agent gets its own credentials, so it is always clear which agent did what. Service accounts also work and are still widely used.
  • ✓No downloaded key files. Key files can leak. Where possible, attach the identity to the service so that no key file exists.
  • ✓Central rules for tool access. Use the registry for approved tools and the gateway for policies, so the rules live in one place rather than inside each agent.
  • ✓Separate environments. Development, testing, and production should live in different projects with different access rules.
  • ✓Regular reviews. Access that was needed during development is often not needed in production.

Example: Giving an Agent Access

Suppose an agent needs to call a Gemini model and read files from one storage bucket. The steps below use a service account, the simplest and most common setup. Agent Identity follows the same least-privilege idea.

  1. Create an identity for the agent.
  2. Grant it permission to use the platform's models.
  3. Grant it read access to only the required bucket.
  4. Attach this identity to the Cloud Run service or the Agent Runtime deployment.
# 1. Create a dedicated service account for the agent
gcloud iam service-accounts create support-agent-sa \
  --display-name="Support Agent"

# 2. Allow the agent to use the platform's models
#    (the role ID still uses the older "aiplatform" name)
gcloud projects add-iam-policy-binding PROJECT_ID \
  --member="serviceAccount:support-agent-sa@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/aiplatform.user"

# 3. Allow the agent to read only one bucket
gcloud storage buckets add-iam-policy-binding gs://my-docs-bucket \
  --member="serviceAccount:support-agent-sa@PROJECT_ID.iam.gserviceaccount.com" \
  --role="roles/storage.objectViewer"

Part 7

How to Get Started

  1. Create a Google Cloud account. Sign in with a Google account and set up billing. New users often receive free credits, and there is also a free Express mode for trying things out.
  2. Create a project. Give it a clear name, such as agent-dev, and note the project ID.
  3. Enable billing and set a budget alert so costs do not come as a surprise.
  4. Enable the required APIs. The platform's API must be switched on before it can be used.
  5. Install the gcloud CLI, sign in, and select the project.
  6. Set up access. Create an identity for the agent and assign least-privilege roles.
  7. Try a model. Use AI Studio or the platform console to test prompts with Gemini.
  8. Build the first agent. Use ADK, or Agent Studio if low-code is preferred, and give it one simple tool.
  9. Test it. Use Agent Simulation to try it on made-up conversations before real users see it.
  10. Deploy it. Use Agent Runtime so the agent is available beyond the developer's laptop. It is registered in Agent Registry automatically.
  11. Add monitoring. Turn on logging and observability, then review how the agent behaves with real inputs.
# Basic setup commands
gcloud auth login
gcloud config set project PROJECT_ID
gcloud services enable aiplatform.googleapis.com run.googleapis.com
Part 8

Putting It Together: Example Agent Architecture

A customer support agent shows how the parts connect.

  1. A user sends a question through a web or chat interface.
  2. The request reaches a backend running on Cloud Run.
  3. The backend calls the agent, which is built with ADK and hosted on Agent Runtime.
  4. The agent uses a Gemini model to understand the question.
  5. If needed, it searches company documents using RAG Engine or Vector Search, backed by Cloud Storage.
  6. If needed, it calls a tool API to check an order stored in Cloud SQL. The call passes through Agent Gateway, which checks the agent\u2019s identity and the rules for that tool.
  7. Memory Bank keeps useful facts about the customer, so the next conversation can pick up where this one stopped.
  8. Secrets are read from Secret Manager, and Model Armor screens what goes in and out.
  9. Agent Observability and Cloud Logging record the whole journey for later review.
Summary

The journey so far

  • ✓Agents often start as simple personal projects, but enterprise needs such as scale, security, and cost control call for a full platform.
  • ✓GCP is a good fit because it provides models, hosting, data, security, and monitoring in one place.
  • ✓Vertex AI is now the Gemini Enterprise Agent Platform, built around four ideas: build, scale, govern, and optimize.
  • ✓The newer pieces to know are Agent Runtime, Memory Bank, Agent Identity, Agent Registry, and Agent Gateway.
  • ✓GCP is organized into organizations, folders, and projects, and the project is the main working unit.
  • ✓The right choice depends on the need. Start simple and add services only when they are required.
  • ✓Access is controlled through IAM. The guiding rule is least privilege, with a separate identity for each agent.
  • ✓Getting started takes a few steps: create a project, enable billing and APIs, set up access, test a model, build an agent, deploy it, and monitor it.
Note for the presenter

Google renamed its AI platform in April 2026 and is still adding features, and some features may still be in preview. Names, availability, and pricing should be confirmed in the official Google Cloud documentation shortly before the session.
